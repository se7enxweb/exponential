# Exponential 6.0.15

Not released yet. The 6.0.15 line follows v6.0.14 (2026-06-07); no tag `v6.0.15` existed on 2026-10-02. This page
lists what the line contains on that date.

Read this page if you run 6.0.14 or older and plan to move to the current code, or if you want to know what the
line brings. It is long because the line is: four months of work. Use the sections by period.

## Upgrading

Follow the [Upgrading guide](../../guides/upgrading.md), part C. Then read the checklist of each period you pass,
in this order:

1. [Behaviour changes of July and August 2026](../../bc/6.0/behaviour-changes-2026-07-08.md)
2. [Behaviour changes of 16 to 30 September 2026](../../bc/6.0/behaviour-changes-2026-09b.md)
3. [Behaviour changes of 1 to 2 October 2026](../../bc/6.0/behaviour-changes-2026-10.md)
4. [Upgrade notes: e-mail preferences and the mail gate](../../bc/6.0/mail-preferences.md)

The database update for the line is `update/database/<engine>/6.0/dbupdate-6.0.0-6.0.15.sql`, followed once by
`php update/common/scripts/6.0/createaudittables.php`.

- **Failed mail is kept**: a notification the mail transport refuses stays in the queue and is tried again at every run for

## 4 October 2026: e-mail preferences and consent

The upgrade checklist is [Upgrade notes: e-mail preferences](../../bc/6.0/mail-preferences.md). The system is described in
[the user's guide](../../features/6.0/mail-preferences.md), [the administrator's guide](../../guides/mail-preferences-administrator.md),
[the developer's guide](../../guides/mail-preferences-developer.md), [the specification](../../specifications/6.0/mail-preferences.md)
and [the law checklist](../../specifications/6.0/mail-preferences-compliance.md) (CAN-SPAM, GDPR and ePrivacy, CCPA/CPRA,
CASL, RFC 8058).

### Added

- **E-mail preferences**: one page (`/mailpreferences/settings`, also in the administration under **My e-mail
  preferences**, and without login by a personal link) where every person turns each optional kind of e-mail on or off,
  chooses how often, turns all optional e-mail off with one button, sees the history of their choices and downloads their
  data as JSON or CSV. Every optional kind is off until the person turns it on. Essential mail (account security, orders,
  legal notices, admin alerts) is listed and always sent.
- **The mail gate** in `eZMailTransport::send()`, for every transport: mail declares a category with
  `eZMail::setCategory()`; optional mail goes only to people who turned it on, one mail each, with a footer (why, one-click
  unsubscribe, preferences, the organisation and its postal address) and the RFC 8058 headers `List-Unsubscribe` and
  `List-Unsubscribe-Post`. Mail without a category is sent as before and counted.
- **Unsubscribe in one click** (`/mailpreferences/unsubscribe/<token>`), also from the mail program's own button; a page
  opened by a link changes nothing until its button is pressed. **Double opt-in** for newsletters, offers and a new e-mail
  address. **Send me a link** for people without an account.
- **Consent log** of every change with the exact text shown, the source, the IP address and the acting user; **suppression
  list** stored as salted hashes; links encrypted with AES-256-GCM under a site secret; export and erasure that keeps the
  proof of a withdrawal; retention by the cronjob part `mailpreferences` (group `infrequent`).
- Administrator's pages under **Setup > E-mail preferences**: status, categories (create, rename, describe), suppression
  list, consent log with filters and CSV export, a user's preferences. Policies `mailpreferences/administrate` and
  `mailpreferences/export`.
- Commands `exp:mail:status`, `exp:mail:preferences`, `exp:mail:suppression`, `exp:mail:consent`, `exp:mail:gate`.
  [Command reference](../../specifications/6.0/mail-preferences-cli.md).
- Unticked boxes for the optional kinds on the registration form; English and German texts.
- Tables `expmail_category`, `expmail_preference`, `expmail_consent_log`, `expmail_suppression`, `expmail_pending` in the
  kernel schema and the database update.
- Tests: `MailPreferencesCoreTest` (20 cases of the core and the gate) and `MailPreferencesComplianceTest` (one case per

### Added

  a part, as `host_uri` already could: the new setting `site.ini [SiteAccessSettings] HostMatchMethod` (`strict` by

- Security: `settings/edit` and the remove action of `settings/view` took the INI file, the siteaccess and the place
  to write from the request as they were, so a POST with `../` in `INIFile`, `SiteAccess` or `SettingPlacement` could
  write an `.append.php` file outside the settings tree. Every name is now checked against what the installation lists
  (the INI files found, `RelatedSiteAccessList`, the active extensions), block and setting names must be ones eZINI
  reads back, read-only settings (`[eZINISettings] ReadonlySettingList`) are refused, and the values shown on the edit
  page are escaped. `eZINI::save()` already refused line breaks and `*/` in values.
- Security: secrets were shown in plain text (the values of six settings named like Password, Token or Key in
  `site.ini` and one in `velocity.ini`), also in the edit field. Their values are now masked everywhere on both pages, never searched and
  never put back into a form; a secret left empty on the edit page keeps its value.
- A saved setting did not take effect: `config.php` switches eZINI's file time check off, and the page never cleared
  the INI cache, so neither PHP-FPM nor Velocity used the new value. Saving and removing now clear the INI cache and say
  which caches were cleared, and whether Velocity must be restarted for the setting.
- The origin of array elements was wrong after a reset (`Name[]`) in a later file: eZINI's placements keep counting
  past a reset, so 1833 of 21542 array elements on alpha were attributed to a file they do not come from. The origin
  is now worked out from the files themselves in eZINI's load order (`expSettingsChain`), checked against eZINI for
  every setting of every file in every siteaccess (41728 settings, no difference).
- The page is redesigned for the admin and admin4 designs: figures for the file, the files read in their order, a card
  per block with a jump list, every setting with its value in effect, its origin, its default when changed and its
  whole override chain (what each file does: sets, empties the array, adds an element, sets a key; in effect or
  overridden), arrays as numbered lists with the origin of each element. The edit page shows the chain before the form,
  explains each place to save, and fills an array's field with an empty first line so saving it as shown replaces the
  array instead of adding the same elements again. Every form field, button and template variable of the old pages is
  kept; the pages work without JavaScript.
- `settings/edit` accepts the setting names eZINI accepts (`Class_identifier`, names with `-`, `@`, `*`), and an empty
  array can be saved.

### Added

- Search across settings (block, name and value) in one file or in every INI file of a siteaccess, a filter for the
  settings changed from the default, and a comparison of a file between two siteaccesses.
- "Not in effect yet": the page compares the files with the values the serving process runs with (PHP-FPM on 443,
  Velocity on 8080) and lists the settings still waiting for an INI cache clear. Files of the load order the server
  cannot read are named.
- `site.ini [SettingsViewSettings]` `MaskedNameList[]`, `UnmaskedNameList[]` and `MaskRevealLastCharacters` (which
  names are secrets, on top of the rule of `exp:ini` and the audit log), and `RestartSettingList[]` (the settings

- Classes `expSettingsChain`, `expSettingsSecretRule`, `expSettingsTarget` and `expSettingsPage`
  (`kernel/classes/ini/`). Guide: [The settings page](../../guides/settings-page.md). Tests: `expSettingsPageTest`

## 6 October 2026: the cache preloader

### Updated

- **Setup > Preload** (`setup/preload`) is redesigned for the admin and admin4 designs: a status bar with the run
  going on (site, start, a progress bar of pages warmed against the page limit, the address being requested, Stop)
  or the last run, the live output with the figures of the run when it ends, a form that explains its fields, which
  server's caches a run warms (Apache/PHP-FPM and Velocity share the view cache, image aliases and compiled templates;
  Velocity's response cache keeps a page `DefaultTtl` seconds only), the command and a crontab line for the choices
  made, and the last runs with duration, pages, image aliases made and failures with their addresses, status codes
  and linking pages. The page works without JavaScript (the form posts `Action=start|dryrun|stop`, the names
  `setup/preloadjob` takes) and picks a running run up again when it is opened. Every template variable of the
  earlier page is kept.
- One preload runs at a time: a run holds a lock (`var/<var dir>/preload/run.lock`) from the page, the shell and cron
  alike; a second one is refused (409 from `setup/preloadjob`, exit code 2 from the command). Each run writes a status
  file (`<id>.json`) beside its events, so a run whose process is gone is reported as ended instead of after two
  minutes without output, a fatal error is recorded with its message, and the runs of the shell are listed with the
  others. The last 20 runs are kept.
- `bin/php/preload.php` runs the same crawler as the page (`expPreloadJob::execute()`) instead of `wget` and
  `curl`, and writes nothing to `/tmp`. New options: `--max-pages` (default 1000), `--max-depth`, `--images`,
  `--dry-run`, `--target`. The last three lines of its output say how the run ended, the pages warmed and the
  image aliases made.
- The address of a siteaccess is worked out from `MatchOrder` and every match setting, as a request is matched
  (`expPreloadAddress`): a `HostMatchMapItems[]` entry with a third field (`start`, `end`, `part`) and
  `HostMatchMethod` reach the same siteaccess as for a visitor, `URIMatchType=map` and `HostUriMatchMapItems[]` give
  their own prefixes, and an address the matching does not send to the siteaccess is warned about.
- `setup/preloadstream` no longer runs a crawl inside the request (it held a worker for minutes and started a load from
  a plain GET); it answers the events of the run going on or the last one.
- The preloader takes links and images from the page's own markup only: nothing inside `<script>`, `<template>`,
  `<style>` or comments, and no value that holds a quote, a JavaScript or template expression (`' +`, `${`,
  `{{ }}`) or whitespace. Inline scripts that build markup in strings were reported as broken links
  (`/' + esc(p.path) + '`). Velocity's own panel (`/Q/...`) is never requested.
- The preloader warmed only the front page of a site whose `SiteURL` already ends in its siteaccess prefix (uri
  matching, `latest.demo.exponential.earth/site`): the prefix was rightly not added twice, so the site was taken for
  one matched by its host, and every `/site/...` link was dropped as another siteaccess's. The site is now everything
  below the path of `SiteURL` plus the prefix, in every matching mode (host, uri, host_uri, an installation in a
  folder). Phase 1 also warms the section pages, the top level pages the starting pages link to (`/site/fitness`),
  when `URLTranslationKeyword` names none.

### Added

- What to warm: **Also check the images on each page** (`--images`) requests every image the warmed pages show, once,
  and lists the missing ones with the pages that show them. **Image aliases made** counts the alias files the
  rendered pages created during a run.
- **Dry run** on the page and `--dry-run` from the shell: the address, the prefix, the starting pages, the limits and
  the command, without a request.
- `GET setup/preloadjob/status` (the run going on and the last runs), `POST Action=dryrun`.
- `expPreloadAddress`, `expPreloadLock`, `expPreloadHistory`; guide [Preloading caches](../../guides/preloading-caches.md).
  Tests: `expPreloadAddressTest`, `expPreloadLockAndHistoryTest` (no database).

## 6 October 2026: faster access arrays for users with many role assignments

### Updated

- The access array of a user (`eZRole::accessArrayByUserID()`) is built from the policies, limitations and values of
  all the user's roles loaded in three queries, the limitations of a policy are turned into their part once for all
  the assignments of its role, and the parts are merged in one call. A user with 600 subtree assignments (120
  teamrooms × 5 member roles of 20 policies) took 3,550 ms and about 48,600 queries, now 244 ms and 4 queries. The
  array is the same, in the same order (the values of a limitation by value, as read one by one). New setting
  `site.ini [RoleSettings] AccessArrayPrefetch` (`enabled`; `disabled` builds it role by role). Guide:
  [Faster access arrays](../../features/6.0/access-array-prefetch.md). Tests: `eZPolicyPrefetchedAccessArrayTest` (no
  database), `eZRoleAccessArrayPrefetchLiveTest` (live).
- Fixed (in the same change, before release): the values of a limitation loaded ahead came in the order of their ids
  instead of by value; while the rows were loaded, a role, policy or limitation outside them was answered as having
  none (a policy then as unlimited) instead of asking the database; an IN () list could pass Oracle's 1000 (now at
  most 500 ids per query); a failed query left policies without their limitations, that is unlimited (the array is
  now built role by role then); a build inside a build dropped the outer one's rows. Compared on alpha with `===`
  against the code before for every user, assignee and throwaway roles of every limitation kind: identical; 177,651
  queries and 14.3 s for 31 subjects before, 104 and 1.6 s now.

## 6 October 2026: the upgrade check

### Added

  table (missing tables, tables not in the schema, changed fields and indexes with their shipped and current
  definition), the SQL per table, what removes something, and engine notes. Display only; nothing is run.

  findings as CSV. Guide: [The upgrade check](../../guides/upgrade-check.md).

  files, extension manifests, unlisted and unordered lines, the downloads, and the schema report.

### Updated

- **Setup > Upgrade check** (`setup/systemupgrade`) is redesigned for the admin and admin4 designs, light and dark,
  with a module-local `setup/systemupgrade_exp_style.tpl`: the version, the manifest's entries and dates and how many
  active extensions carry a manifest; the two checks side by side; the file result grouped by state with a search,
  a filter by state and by extension and what to do about each kind of finding; the database result table by table
  with its SQL; the time each check took. **Download CSV**, **Download text** and **Download SQL**
  (`DownloadFileReportButton`, `DownloadSchemaReportButton`) send the report as a file. `MD5CheckButton`,
  `DBCheckButton` and the template variables `md5_result`, `failure_reason`, `upgrade_sql` and `mongo_*` are kept;
  new ones are `file_report`, `file_groups`, `schema_report`, `upgrade_info` and `upgrade_check`.
- The database check no longer calls a database consistent while hiding differences, nor inconsistent over noise:
  differences the engine's schema handler writes no SQL for (on SQLite, 19 tables whose `longtext` reads as `text`
  or whose `AUTOINCREMENT` key reads as `int`) are listed as engine notes and do not fail the check.
- A manifest with CRLF line ends is read like one with LF (the command line check reported every line as missing);
  a manifest line naming a path outside the installation is skipped and reported instead of being read; an empty
  or unreadable `share/filelist.md5` fails the check with its own message instead of passing.
- The audit event `system.upgrade.run` counts the findings of the new reports and names the format of a download.
- The SQLite schema reader reads a key declared `integer NOT NULL PRIMARY KEY AUTOINCREMENT` as `auto_increment`
  (it read `int NOT NULL DEFAULT 0`: expbookmark_folder and the five expmail_* tables), and the database check on
  SQLite compares only what SQLite can tell apart (`eZSQLiteSchema::normalizeForComparison()`: text and longtext,
  the width of an auto_increment key, a default left out or written as false), writing the SQL from the shipped
  definitions. The 19 engine notes on an SQLite installation are gone; a missing field, another type or length,
  NOT NULL and another default still show. Test: `expSQLiteSchemaReaderTest` (a throwaway SQLite file).

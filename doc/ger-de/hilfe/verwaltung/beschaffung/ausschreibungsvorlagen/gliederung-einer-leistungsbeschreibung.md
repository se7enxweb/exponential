# Gliederung einer Leistungsbeschreibung: ein Ausschreibungsgerüst für ein CMS im öffentlichen Sektor

Diese Seite richtet sich an Beschaffungsstellen, die ein Ausschreibungsdokument für eine Website oder ein Intranet auf
Grundlage eines Content-Management-Systems zusammenstellen, mit Leistungen wie Bau, Hosting, Support und Schulung. Sie
gibt das Gerüst des Dokuments, sagt, was jeder Abschnitt enthält, und verlinkt die Klauselvorlagen und Seiten zu
Anforderungen dieser Hilfe, die ihn füllen.

**Vorlage** - an Ihre Vergaberegeln anpassen; keine Rechtsberatung

> **Hinweis** Diese Seite beschreibt Funktionen und übliche Praxis; sie ist keine Rechtsberatung. Prüfen Sie das für
> Ihre Organisation geltende Recht mit Ihrer Rechtsberatung.

## Das Gerüst

```text
<Organization> - Request for proposals <reference>
Web content management system and related services

PART A  INVITATION
  A1  Introduction and background of <organization>
  A2  Purpose and scope of the procurement
  A3  Procedure, timetable and contact point
  A4  Eligibility and exclusion grounds (per <applicable rules>)
  A5  Evaluation method and award criteria
PART B  REQUIREMENTS
  B1  Current situation (sites, content volume, languages, users, integrations)
  B2  Functional requirements                     -> annex B2
  B3  Accessibility requirements                  -> annex B3
  B4  Security requirements                       -> annex B4
  B5  Privacy and data protection requirements    -> annex B5
  B6  Languages                                   -> annex B6
  B7  Hosting and data location                   -> annex B7
  B8  Integration                                 -> annex B8
  B9  Operations, support and maintenance         -> annex B9
  B10 Training and documentation                  -> annex B10
  B11 Migration of existing content (if any)      -> annex B11
PART C  CONTRACT TERMS
  C1  Licensing, source code and intellectual property
  C2  Service levels
  C3  Acceptance testing
  C4  Vulnerability handling and patching
  C5  Exit, data return and transition
  C6  Warranty of no lock-in
  C7  Term, renewal, price review
PART D  RESPONSE FORMS
  D1  Compliance matrix (one row per requirement)
  D2  Technical proposal
  D3  Implementation plan and team
  D4  Pricing schedule (one-off and recurring)
  D5  Declarations
```

## Teil A: die Aufforderung

- **A1-A2**: Beschreiben Sie die Organisation und den Zweck in einfacher Sprache; sagen Sie, welche Websites zum Umfang
  gehören.
- **A3**: Nennen Sie die Termine für Fragen, Vorführungen und die Abgabefrist. Planen Sie einen Proof of Concept, sagen
  Sie es hier.
- **A5**: Veröffentlichen Sie die Gewichtung jedes Kriteriums, bevor Angebote eingehen. Die Seiten zur Bewertung dieses
  Abschnitts zur Beschaffung enthalten Bewertungsbögen.

## Teil D: die Antwortformulare

Eine Erfüllungsmatrix, die die Bieter ausfüllen, hält Antworten vergleichbar:

```text
| Req. id | Requirement (short) | Met: Yes / Partly / No / Planned | Evidence (document, section, setting, test) | Gap and plan |
|---------|---------------------|----------------------------------|---------------------------------------------|--------------|
| ACC-02  | Admin WCAG 2.2 AA   |                                  |                                             |              |
```

Fragen Sie einmalige und wiederkehrende Kosten getrennt ab (Bau, Migration, Hosting je Jahr, Support je Jahr, Schulung,
Upgrades), ohne Zeile für Lizenzgebühren bei GPL-Software, es sei denn, der Bieter fügt proprietäre Komponenten hinzu.

## Vor der Veröffentlichung

- Jedes „muss“ hat eine Prüfmethode ([Prüfbare Anforderungen schreiben](../anforderungen/pruefbare-anforderungen-schreiben.md)).
- Keine Anforderung nennt ein Produkt oder eine Marke, es sei denn, Ihre Regeln erlauben es.
- Kein „muss“ verlangt Nachweise, die der Markt nicht liefern kann
  ([Was Exponential nachweisen kann und was nicht](../anforderungen/was-exponential-nachweisen-kann-und-was-nicht.md) zeigt typische Lücken).
- Die Rechtsberatung hat Teil C geprüft.

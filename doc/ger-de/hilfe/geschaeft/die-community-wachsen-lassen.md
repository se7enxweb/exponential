# Die Community wachsen lassen

Diese Seite richtet sich an Vertrieb und Marketing sowie an Projektleiter, die möchten, dass mehr Menschen Exponential
nutzen, darüber sprechen und dazu beitragen. Sie beantwortet: Welche Kanäle gibt es, wie gelangen Menschen vom ersten
Kontakt zur Mitarbeit, was kann Ihre Organisation jeden Monat tun, und woran erkennen Sie, ob es wirkt? Sie verwendet
nur die Kanäle, die die Dokumentation nennt; sie erfindet keine Programme, Veranstaltungen oder Zahlen.

> **Hinweis**
> Eine Community wächst, wenn Menschen Hilfe bekommen, ihre Beiträge angenommen sehen und andere wie sich selbst
> finden. Ihre Aufgabe ist es, Menschen im richtigen Moment an den richtigen Ort zu führen, nicht einen parallelen
> Kanal aufzubauen.

## Der Trichter für Mitwirkende

Menschen durchlaufen Stufen. Auf jeder Stufe gibt es einen dokumentierten nächsten Schritt und etwas, das Sie tun
können, um ihn zu erleichtern.

| Stufe | Wer sie sind | Ihr nächster Schritt | Wie Sie helfen | Quelle |
|---|---|---|---|---|
| 1. Aufmerksam | Hat den Namen gehört | Liest über das Projekt | Verlinken Sie die Seiten der Foundation und von 7x in Ihrem Material | [Wer ist die Exponential Foundation?](../wer-ist-die-exponential-foundation.md) |
| 2. Benutzer | Betreibt oder bearbeitet eine Site | Nutzt die Hilfe, fragt in den Foren | Weisen Sie Redakteure auf das Dashboard der Hilfe und die Seiten für ihre Zielgruppe hin | [Das Hilfesystem](../../../en/us/features/6.0/help-system.md) |
| 3. Meldender | Stößt auf ein Problem | Legt ein gutes Issue an | Erklären Sie die Seite **Fehler melden** und eine gute Fehlerbeschreibung | [Wenn etwas schiefgeht](../wenn-etwas-schiefgeht.md#eine-gute-fehlerbeschreibung) |
| 4. Dokumentierender oder Übersetzer | Kennt einen Teil gut | Verbessert eine Hilfeseite mit *Auf GitHub bearbeiten*, vervollständigt eine Übersetzung | Geben Sie in Projekten Zeit dafür | [Freie Dokumentation](../freie-dokumentation.md#anderen-helfen), [Sprachen](../../../en/us/languages.md#8-adding-or-completing-an-administration-translation) |
| 5. Mitwirkender | Kann Code ändern | Sendet einen Pull-Request | Installieren Sie vom ersten Tag an mit Git-Klonen | [Mit Git entwickeln](../mit-git-entwickeln.md), `CONTRIBUTING.md` |
| 6. Reviewer oder Maintainer | Trägt regelmäßig bei | Prüft die Arbeit anderer, pflegt eine Erweiterung | Würdigen Sie die Arbeit öffentlich | `CONTRIBUTING.md`, „Code Reviews“ |

Was Stufe 5 attraktiv macht und dokumentiert ist:

- „Every pull request is merged, and its commits are kept as the contributor wrote them and never rewritten“: Jeder
  Pull-Request wird gemergt, und seine Commits bleiben so, wie der Mitwirkende sie geschrieben hat
  ([Continuous Integration](../../../en/us/bc/6.0/ci.md#the-commit-message-policy)).
- Beiträge bleiben frei: „any modifications made to the project are also released under the same GPLv2 or later
  license“ (`CONTRIBUTING.md`), jede Änderung am Projekt wird also unter derselben Lizenz veröffentlicht.
- Eine Korrektur „reaches every site in the next release“, sie erreicht mit dem nächsten Release jede Site
  ([Wenn etwas schiefgeht](../wenn-etwas-schiefgeht.md#noch-besser-die-korrektur-mitschicken)).

Die Führungsseite dieser Leiter, mit einem Plan für 30, 60 und 90 Tage, steht unter
[Zur Führungskraft in der Exponential-Community werden](../fuehrung/community-leiter-werden.md).

## Beiträge, die kein Code sind

Menschen aus Marketing und Projektarbeit können direkt beitragen. Dies sind dokumentierte, konkrete Gelegenheiten.

| Beitrag | Warum er wichtig ist | Wie | Quelle |
|---|---|---|---|
| Eine maschinengestützte Übersetzung prüfen | Spanisch, Französisch, Ukrainisch, Hebräisch, Latein und Klingonisch wurden maschinengestützt übersetzt; eine Prüfung ist „the quickest win“, der schnellste Gewinn | Die Administration in der Sprache lesen und falsche Texte melden oder korrigieren | [Sprachen](../../../en/us/languages.md#8-adding-or-completing-an-administration-translation) |
| Fehlende Texte übersetzen | Seit 6.0 kamen etwa 10.000 Texte hinzu; sie zu übersetzen ist für jede unvollständige Sprache „the most useful work“, die nützlichste Arbeit | Qt Linguist oder ein XML-Editor, dann ein Pull-Request | [Sprachen](../../../en/us/languages.md#8-adding-or-completing-an-administration-translation) |
| Eine Hilfeseite verbessern | Bessere Hilfe bedeutet weniger Support-Fragen | *Auf GitHub bearbeiten* auf der Seite, dann ein Pull-Request; angenommen unter der GNU FDL 1.3 oder höher | [Freie Dokumentation](../freie-dokumentation.md#anderen-helfen) |
| Eine Hilfeseite übersetzen | Eine übersetzte Seite „helps every reader of that language“, hilft jedem Leser dieser Sprache | Wie oben | [Freie Dokumentation](../freie-dokumentation.md#anderen-helfen) |
| Ein Tutorial oder einen Blogbeitrag schreiben | Neue Benutzer finden Antworten | Auf Share oder Ihrer eigenen Site veröffentlichen, zurückverlinken | [Wer ist 7x?](../wer-ist-7x.md#die-community) |
| eZpedia bearbeiten | Hält die Enzyklopädie nützlich | Auf der Site bearbeiten (GFDL) | [Wer ist 7x?](../wer-ist-7x.md#die-community) |
| Klare Fehler melden | Schnellere Korrekturen für alle | Die Seite **Fehler melden** | [Wenn etwas schiefgeht](../wenn-etwas-schiefgeht.md) |
| Eine Frage im Forum beantworten | Der nächste Benutzer bekommt Hilfe | Foren, Telegram | [Wer ist die Exponential Foundation?](../wer-ist-die-exponential-foundation.md#orte-der-community) |

## Was Ihre Organisation tun kann

Ein Plan, den Ihre Organisation übernehmen und anpassen kann. Jeder Punkt nutzt einen dokumentierten Kanal.

### Jeden Monat

- [ ] Mindestens `<n>` Fragen in den Foren oder auf Telegram beantworten (eine verantwortliche Person benennen).
- [ ] Einen nützlichen Artikel aus dem [Redaktionskalender](#eine-vorlage-für-einen-redaktionskalender) veröffentlichen.
- [ ] Eine Support-Frage, die Ihr Team beantwortet hat, in eine Verbesserung einer Hilfeseite verwandeln (Pull-Request).
- [ ] In den Issue-Trackern nach Issues sehen, die Ihre Kunden gemeldet haben, und ergänzen, was Sie wissen.

### Bei jedem Release

- [ ] Das Changelog des neuen Release lesen ([Changelogs](../../../changelogs/README.md)) und die Monatsseiten der
      [Geschichte](../../../en/us/history/README.md).
- [ ] Aus dem Changelog einen kurzen Beitrag „Was ist neu für Redakteure“ schreiben, mit Links zu den Funktionsseiten.
- [ ] Ihren Kunden sagen, welche Hilfeseiten sich geändert haben.

### Bei jedem Projekt

- [ ] Mit Git-Klonen installieren, damit Korrekturen als Pull-Requests zurückfließen können ([Mit Git entwickeln](../mit-git-entwickeln.md)).
- [ ] Zeit dafür einplanen, Korrekturen und Dokumentation an das Upstream-Projekt zu senden (siehe [Schätzen und Abgrenzen mit Erweiterungen](../fuehrung/schaetzen-und-abgrenzen-mit-erweiterungen.md)).
- [ ] Den Kunden fragen, ob eine Fallstudie möglich ist, mit Einwilligung
      ([Fallstudien und Content-Marketing schreiben](fallstudien-und-content-marketing.md)).
- [ ] Die Redakteure des Kunden bei der Übergabe mit der Hilfe und den Foren bekannt machen.

### Jedes Jahr

- [ ] Über ein Sponsoring der Foundation oder von 7x entscheiden.
- [ ] Prüfen, welche Erweiterungen Ihre Projekte nutzen und ob Sie bei der Pflege einer davon helfen können.

## Kunden in die Community bringen

Kunden sind die größte potenzielle Community. Geben Sie jedem Kunden bei der Übergabe Folgendes mit:

```text
WELCOME TO THE EXPONENTIAL COMMUNITY                         <customer>

Your site runs on Exponential <6.0.x>, open source software under the GNU GPL.

Help in your administration     Help (the "?" in the header) or /exphelp/dashboard
Ask questions                   share.exponential.earth/forums   or Telegram: t.me/exponentialcms
Report an error                 Help > Report an error  (never put passwords or personal data in an issue)
Security problems               privately, as described in SECURITY.md
Who is behind Exponential       Help: "Who is 7x?" and "Who is the Exponential Foundation?"
Improve the help                "Edit on GitHub" on every help page
Your contact at <your organization>   <role, contact channel>
```

## Das Projekt finanziell unterstützen

Die dokumentierten Wege, aus [Wer ist die Exponential Foundation?](../wer-ist-die-exponential-foundation.md#unterstützen-oder-mitmachen):

| Weg | Finanziert | Adresse |
|---|---|---|
| Die Foundation sponsern | „the open-source project itself“, das Open-Source-Projekt selbst | `github.com/sponsors/exponentialcms` oder über `foundation.exponential.earth` |
| 7x sponsern | „the company that keeps the lights on“, das Unternehmen, das den Betrieb am Laufen hält | `github.com/sponsors/se7enxweb`, `sponsor.se7enx.com`, PayPal (README) |

Die Foundation gibt an, dass Spenden in den Vereinigten Staaten steuerlich absetzbar sind; jeder Käufer oder Sponsor
muss das mit seinem eigenen Steuerberater klären. Wofür ein Sponsoring der Foundation bezahlt, steht unter
[Was die Foundation finanziert](../wer-ist-die-exponential-foundation.md#was-die-foundation-finanziert).

## Eine Vorlage für einen Redaktionskalender

Planen Sie Inhalte für die Community ein Quartal im Voraus. Knüpfen Sie sie an Dinge, die wirklich geschehen:
Releases, Monate der Geschichte, neue Hilfeseiten, Ihre eigenen Projekte.

```text
COMMUNITY CONTENT CALENDAR                               Quarter: <Q / year>
Owner: <role>                                            Review: monthly

| Week | Theme                    | Piece                                  | Channel                 | Owner  | Source to cite              | Status |
|------|--------------------------|----------------------------------------|-------------------------|--------|-----------------------------|--------|
| 1    | Getting started          | "Install Exponential in one command"   | blog, forum post        | <role> | help: getting-started.md    | idea   |
| 2    | Help the helpers         | Answer 5 forum questions               | forums                  | <role> | -                           | plan   |
| 3    | Editors                  | "Build a page with the layouts editor" | blog, newsletter        | <role> | help: layouts-editor.md     | draft  |
| 4    | Languages                | Call for translation reviewers         | forum, Telegram         | <role> | doc/en/us/languages.md section 8  | plan   |
| 5    | History                  | "This month in Exponential history"    | blog                    | <role> | doc/en/us/history/<month>.md      | idea   |
| 6    | Release                  | "What is new in <version>"             | blog, forum, newsletter | <role> | doc/changelogs/6.0/<v>.md   | wait   |
| 8    | Case study (with consent)| <customer story>                       | site, newsletter        | <role> | approved text               | consent|
| 10   | Contribute               | "Your first pull request"              | blog, forum             | <role> | help: develop-with-git.md   | idea   |
| 12   | Quarter review           | Measures, next quarter                 | internal                | <role> | measures below              | -      |

Status values: idea, plan, draft, review, approved, published, wait (for a release), consent (case study)
```

Regeln für den Kalender:

- Jeder Beitrag nennt seine Quelle; Aussagen über das Produkt verlinken auf eine Hilfeseite.
- Beiträge zu einem Release warten auf das Release; kündigen Sie eine Version nie an, bevor ihr Tag existiert (ein
  veröffentlichter Tag wird nie geändert, `SECURITY.md`).
- Fallstudien folgen dem Ablauf für Einwilligung und Freigabe.
- Verwenden Sie die Produktnamen aus [Marken- und Namensregeln](marken-und-namensregeln.md).

## Messen, was Sie tatsächlich sehen können

Die Quellen veröffentlichen keine Statistiken zur Community, und diese Seite erfindet keine. Messen Sie, was Ihre
Organisation selbst beobachten und zählen kann:

| Kennzahl | Wie zählen | Wo |
|---|---|---|
| Antworten Ihres Teams in den Foren | Die Beiträge Ihres Teams zählen | Die Foren |
| Issues, die Ihr Team angelegt oder zu schließen geholfen hat | Nach Ihren Konten filtern | Die Issue-Tracker auf GitHub |
| Pull-Requests, die Ihr Team gesendet hat und die gemergt wurden | Nach Ihren Konten filtern; `git log --grep="Merge pull request"` in einem Klon | GitHub, `git log` |
| Hilfeseiten, die Ihr Team verbessert hat | Ihre Pull-Requests, die `doc/` betreffen | GitHub |
| Übersetzungstexte, die Ihr Team vervollständigt hat | `php bin/php/ezchecktranslation.php <code> --allow-root-user` vorher und nachher | [Sprachen](../../../en/us/languages.md#8-adding-or-completing-an-administration-translation) |
| Kunden, die Sie mit der Community bekannt gemacht haben | Ihre Checkliste für die Übergabe | Ihre Unterlagen |
| Aus dem Kalender veröffentlichte Inhalte | Ihr Kalender | Ihre Site |
| Aktivität im gesamten Projekt | Commits und gemergte Pull-Requests, mit den Befehlen, die die Quelle nennt | [Wer ist 7x?](../wer-ist-7x.md#7x-in-zahlen) |

Berichten Sie Trends über Quartale, keine einmaligen Zahlen, und immer mit dem Datum der Zählung.

## Verhaltensregeln für Fürsprecher

- **Seien Sie genau.** Verwenden Sie die Fakten der Hilfe und verlinken Sie sie. Sagen Sie „Die Quellen sagen dazu
  nichts“, wenn das so ist.
- **Seien Sie ehrlich zu Größe und Lücken.** Blähen Sie die Community nicht auf. Laden Sie Menschen ein, sie größer zu
  machen.
- **Achten Sie die Privatsphäre.** Veröffentlichen Sie nie Kundendaten, Passwörter, Schlüssel oder Hostnamen in
  öffentlichen Kanälen ([Wenn etwas schiefgeht](../wenn-etwas-schiefgeht.md#eine-gute-fehlerbeschreibung)).
- **Halten Sie Sicherheitsthemen vertraulich.** Sicherheitsprobleme gehen an die vertrauliche Adresse aus
  `SECURITY.md`, nie in ein Forum.
- **Nennen Sie andere.** Nennen Sie die Menschen und Unternehmen, auf deren Arbeit Sie aufbauen ([Wer ist 7x?](../wer-ist-7x.md#mitwirkende-und-freunde-des-projekts)).
- **Befolgen Sie die Regeln für Beiträge.** Lesen Sie `CONTRIBUTING.md`, bevor Sie Code senden: Branches,
  fokussierte Pull-Requests, die Präfixe der Commit-Nachrichten und das Review. Dort steht auch, dass von allen
  Mitwirkenden erwartet wird, einen Verhaltenskodex einzuhalten; die verlinkte Datei (`CODE_OF_CONDUCT.md`) ist zum
  Zeitpunkt des Schreibens nicht im Repository, fragen Sie also die Maintainer danach, wenn Sie den Text brauchen.
- **Sprechen Sie nicht für das Projekt.** Sofern 7x oder die Foundation Sie nicht darum gebeten haben, sprechen Sie
  für sich selbst oder Ihre Organisation.

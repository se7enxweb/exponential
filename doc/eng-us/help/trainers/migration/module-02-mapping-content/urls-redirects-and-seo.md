# Lesson 2.3: URLs, redirects and search engine metadata

A migration that loses addresses loses search ranking and every link other sites made to it. This lesson teaches the
three ways Exponential keeps an old address, when the web server has to help, and how to test a redirect table
automatically.

## Learning objectives

After this lesson, learners can:

- decide for each old address: same address, 301 redirect, or deliberately gone (410 or 404);
- choose between a node's own alias, a redirecting custom alias, a URL wildcard and a web server rule;
- create and try a URL wildcard in the admin;
- write an automatic test for a redirect table;
- list the search engine metadata to carry over.

## Trainer's notes

### How to present it

Sources: [checklist, sections 4 and 5](../../../../install/migration/checklist.md#4-urls-and-redirects),
[Mapping content, section 10](../../../../install/migration/content-model-mapping.md#10-urls) and
[Links, URL aliases, wildcards and search statistics](../../../../guides/urls-and-aliases.md).

1. **Three decisions** (3 minutes). Every old address is kept, redirected with 301, or deliberately gone.
2. **Three tools in Exponential** (8 minutes):
   - the **node's own URL alias**, when the old path can be the new path (the tree mirrors the old structure);
   - a **custom URL alias** on the node that redirects (301) to its main address, one per old address that differs;
   - a **URL wildcard** (`news/*` to `articles/{1}`) for whole groups that changed in a regular way.
3. **The web server** (3 minutes). Addresses with query strings (`?p=123`, `index.php?id=5`) never reach URL aliases:
   redirect them in the web server, from the same table.
4. **Tests** (3 minutes). Test every row automatically, status and destination, not by sampling. Keep redirects for
   at least a year.
5. **Metadata** (3 minutes). Titles and descriptions map to `xrowmetadata`; canonical, `hreflang` and robots rules
   live in the pagelayout; an XML sitemap after go-live.

### Common questions

**Where is the redirect table generated from?** From the import: remote id to new node, old address to new address
(checklist, section 4). That is another reason for remote ids.

**Which tool for 5 000 blog posts whose path only lost its date part?** If the change is regular, a wildcard or a web
server rule; if not, one redirecting alias per post, generated by the import.

**What happens when a wildcard and an alias both match?** The admin page says it: wildcards are only consulted when no
URL alias matches the address, and the first wildcard that matches is used.

**Does the old address keep working for an in-place upgrade of an old Exponential site?** Yes: the URL alias tables
move with the database ([Older releases](../../../../install/migration/older-releases.md)).

### Pitfalls

- **Testing by clicking.** Ten clicks do not test 3 000 rows. Use a script.
- **Forgetting media addresses.** Old image and PDF addresses are linked from other sites too.
- **Leaving wildcards in a training installation.** Learners remove their wildcard at the end of the exercise.

## Hands-on exercise

Use your own training installation and an administrator account.

1. In the admin, open **Setup > URL wildcards**. Read the explanation at the top of the page.
2. Under **New URL wildcard**, enter `old-news/*` as the address to catch and `news/{1}` as the **Destination**.
   Leave **Redirecting URL** checked.
3. Press **Create**.
4. Under **Try an address**, type `old-news/2026/october` in **Address** and press **Try**. Note which wildcard
   matched and where the address leads.
5. In a terminal, ask the site for the old address and look at the status and the `Location` header (replace the host
   with your training site's address):

   ```bash
   curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' http://localhost/old-news/2026/october
   ```

6. Open the URL alias page of a node of your own, at `/admin/content/urlalias/<node id>`. Read the **Generated
   aliases** list and the **Create new alias** form with **Alias should redirect to its destination**. Do not create
   an alias.
7. In your notes, write a redirect table of five rows for the WordPress scenario: an old permalink, `/?p=123`,
   `/category/news/`, `/wp-content/uploads/2024/05/plan.pdf` and `/wp-login.php`. For each row write the tool (node
   alias, custom alias, wildcard, web server) and the status. Use the table in the
   [WordPress guide, section 4](../../../../install/migration/wordpress.md#4-addresses-and-redirects).
8. Write a test loop for the table: for each row, request the old address and compare status and destination, as
   in step 5.
9. Back on **Setup > URL wildcards**, select your wildcard and press **Remove selected**.

## Expected result

- Step 4: the page shows that `old-news/*` matched and the destination `news/2026/october`.
- Step 5: status `301` and a redirect address ending in `news/2026/october`.
- The redirect table sends `/?p=123` to the web server (query strings never reach URL aliases) and marks
  `/wp-login.php` as 410 or a redirect to the new login.
- After step 9 the wildcard list is empty again.
- The trainer checks step 5 on two screens and one redirect table.

## Quiz

1. Which Exponential tool fits a whole group of old addresses that changed in a regular way?
   A. A global URL alias B. A URL wildcard C. A section D. An object state
2. Why can `index.php?id=5` not be redirected with a URL alias?
3. When is a URL wildcard consulted?
4. How long should redirects be kept, according to the checklist?
5. Name two items of search engine metadata to carry over.

<details>
<summary>Answers</summary>

1. **B** ([checklist, section 4](../../../../install/migration/checklist.md#4-urls-and-redirects)).
2. Query strings never reach URL aliases; handle them in the web server
   ([WordPress guide, section 4](../../../../install/migration/wordpress.md#4-addresses-and-redirects)).
3. Only when no URL alias matches the address; the first matching wildcard wins (the **URL wildcards** page in the
   admin, and [URLs and aliases, section 4](../../../../guides/urls-and-aliases.md#4-url-wildcards)).
4. At least a year (checklist, section 4).
5. Any two of: titles and meta descriptions, canonical addresses, `hreflang`, robots rules, the XML sitemap,
   structured data, analytics and verification tags
   ([checklist, section 5](../../../../install/migration/checklist.md#5-search-engine-metadata)).

</details>

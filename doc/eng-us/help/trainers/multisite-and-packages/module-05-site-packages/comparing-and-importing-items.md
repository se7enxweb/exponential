# Lesson 5.5: Comparing a package with the site and importing single items

Installing a content package on a site that already has content used to be a leap of faith. **Compare** shows, item
by item, how a package differs from the site, and lets you import only what you choose, after a confirmation that
lists exactly what will change. This lesson changes an item on the lab after exporting it, then compares and brings
back one value from the package.

## Learning objectives

After this lesson, learners can:

- open the comparison of a package and read its five statuses;
- filter, sort and search the comparison and open one item side by side;
- import one value of a changed item and keep the others as the site has them;
- state the importer's rules: nothing only on the site is removed, locations are never duplicated or moved.

## Trainer's notes

### How to present it

Source: [Look inside a package, compare it with your site, import single items](../../../../features/6.0/package-compare-and-import.md).

1. **How items are matched** (4 minutes). Content classes by identifier, content objects by remote ID. Both sides are
   serialized by the same code, then normalized per datatype (rich text as canonical XML, relations by remote IDs,
   images and files by name, size and checksum). Translations only on one side and placement are compared too.
2. **The statuses** (3 minutes). **new**, **changed**, **only on the site**, **identical**, **class missing**: each a
   chip with its own glyph and label, so color is never the only signal; the chips also filter.
3. **One item** (3 minutes). Values side by side, removed text struck through, added text underlined, rich text XML at
   hand. **Compare again** rebuilds the cached comparison.
4. **Importing** (5 minutes). With `package/install` on top of `package/read`, rows that are not identical have
   **Import** and a checkbox, next to **Import selected** and **Import all changes of this filter**; an open item has
   **Import this item** and a tick per value. Every import leads to a confirmation that lists what will be set and
   kept. The rules: a new object is created where the package places it; a changed object gets the package's values,
   unticked values keep the site's; locations the site has are never duplicated or moved; something only on the site
   is never removed.

### Common questions

**Does Compare change anything?** No. It is read-only; nothing is installed or stored, only a cached comparison in the
cache directory.

**Why is an item refused?** An object that is not published, whose class differs, or that has no values is refused
before the confirmation, with the reason.

**How many items per request?** At most 25; the result page offers the next step when a filter holds more.

**What about classes?** A changed class is updated in place; an object whose values need a class imported first is
imported together with that class, listed first in the confirmation.

### Pitfalls

- **Comparing a site package.** Compare is for packages that install content; a site package has nothing to install
  on its own.
- **Unpublished drafts.** An object changed only as a draft compares as the published version.
- **Importing everything.** **Import all changes of this filter** with no filter imports every difference; filter
  first.

## Hands-on exercise

Use your training installation and an administrator account, with the package `clubb_content` from lesson 5.3.

1. In the administration, edit the folder *News* below *Site B*: change its name to `News and events` and publish.
2. Open **Setup** > **Packages**, open `clubb_content` and press **Compare**.
3. Read the counts of each status. Which items are **identical**, which **changed**?
4. Filter by **changed**. Open the item *News and events*.
5. Read the values side by side: the old name from the package and the new one on the site.
6. Press **Import this item**, untick every value except the name, and continue to the confirmation.
7. Read the confirmation: what will be set, what kept.
8. Confirm. Read the result.
9. Open the folder in the administration: its name is `News` again. Open **Manage versions** and see the new
   version the import made.
10. Back in the comparison, press **Compare again**: the item is **identical** now.

## Expected result

- Step 3: most items **identical**, the folder **changed**.
- Step 7 lists the name as set and the other values as kept.
- Step 9: the folder is called *News*, in a new version; nothing else on the site changed.
- Step 10: the comparison shows the item **identical**.
- The trainer checks step 7 on the projector before learners confirm.

## Quiz

1. How are content objects of a package matched to the site?
2. Which status does an object have that exists on the site below the package's top node but not in the package?
   A. new B. changed C. only on the site D. class missing
3. True or false: importing a package removes objects that exist only on the site.
4. You untick a value in **Import this item**. What happens to it?
5. Which policies are needed to import?

<details>
<summary>Answers</summary>

1. By remote ID ([Package compare and import](../../../../features/6.0/package-compare-and-import.md#2-compare-a-package-with-the-site)).
2. **C.**
3. **False.** Something only on the site is never removed.
4. It keeps the site's value.
5. `package/install` on top of `package/read`.

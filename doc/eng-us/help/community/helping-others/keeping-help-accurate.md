# Keeping community help accurate

Wrong help costs people hours. These habits keep yours right.

## Contents

1. [Where the facts live](#where-the-facts-live)

## Where the facts live

| Kind of fact | Source |
|---|---|
| What the software does | The code and its settings, the feature pages under `doc/eng-us/features/` |
| What a release changed | The changelogs under `doc/changelogs/` |
| Requirements | `README.md`, [Requirements](../../../install/02-requirements.md) |
| Who leads and operates the project | [Who is 7x?](../../who-is-7x.md), [Who is the Exponential Foundation?](../../who-is-the-exponential-foundation.md) |
| Licenses | `LICENSE`, `CONTRIBUTING.md`, [Free documentation](../../free-documentation.md) |
| Security policy | `SECURITY.md` |
| Conduct | `CODE_OF_CONDUCT.md` |

The longer guide is [Where the facts live](../../advocates/where-the-facts-live.md).

## Checking a claim

1. Find the source above.
2. Try it on a test installation of the current release.
3. Note the version you checked.
4. Link the source when you share the claim.

## Numbers and dates

Numbers such as the count of packages change over time. When you use one, say the date, or recount it with the
command the source page names ([The community and ecosystem as a selling point](../../business/community-and-ecosystem.md)).

## When you were wrong

- Correct it in the same place, visibly: "Correction: ...".
- Do not delete the wrong answer silently; people may have acted on it.
- Thank whoever pointed it out.

The code of conduct asks trainers and advocates to "correct mistakes openly"; the same is good practice for everyone
([Honesty and accuracy](../../advocates/honesty-and-accuracy.md)).

## "Not documented" is an answer

If the documentation and the code do not answer a question, say so. Do not fill the gap with a guess presented as a
fact. Then consider opening an issue so the gap gets documented.

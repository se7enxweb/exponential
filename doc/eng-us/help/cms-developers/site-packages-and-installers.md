# Site packages and installers

This page is for developers who want a site that can be installed again: on a colleague's machine, on staging, for
the next customer. Exponential installs sites from **packages**, and a project can use the same mechanism for its own
classes and starter content, so a new installation is built from files instead of clicks.

## Packages in one paragraph

A package is a folder with a `package.xml` and the files it names, shipped as one `.ezpkg` archive. Types include
`contentclass`, `contentobject`, `extension`, `sitestyle` and `site`. A **site package** (type `site`) requires other
packages and can carry install scripts that set up siteaccesses, extensions, roles and preferences. Installations find
packages on a package server (`settings/package.ini [RepositorySettings] RemotePackagesIndexURL`) and keep downloaded
ones in `var/storage/packages/` ([Site packages: start here](../site-packages/README.md),
[Package types](../site-packages/basics/package-types.md)).

## The three installers

| Installer | Use it for |
|---|---|
| `./console exp:install --apply` | development and scripted installs; SQLite and `sevenx_multisite` by default ([The console install](../../install/07-console-install.md)) |
| The kickstarter (`bin/php/kickstarter.php`, `kickstart.ini`) | unattended installs driven by a settings file ([Kickstarter](../../install/06-kickstarter.md)) |
| The setup wizard in the browser | installs on hosting without a shell ([Setup wizard](../../install/05-setup-wizard.md)) |

All three read the same packages ([How the kickstarter and console use packages](../site-packages/basics/how-the-kickstarter-and-console-use-packages.md)).

## The default site package

`sevenx_multisite` is the default of Exponential 6.0.15. It creates the classes, demo content for two sites, the
siteaccesses (public sites, languages, `admin`, `editor`), roles, and the layouts of Exponential Layouts from the
theme extension's data ([sevenx_multisite](../site-packages/sevenx-multisite/README.md),
[What you have after installing](../site-packages/sevenx-multisite/what-you-have-after-installing.md)). Studying it is
the fastest way to see a complete, production-style setup. Start a project from it, remove what you do not need, and
reuse its classes where they fit ([The sevenx classes](../site-packages/sevenx-multisite/sevenx-classes.md)).

## Packages in your project

Even without a site package, put the database-side parts of your project into packages in your repository:

| Part | Package | How |
|---|---|---|
| Your classes | `contentclass` | **Setup** > **Packages** > **Create new package** > content class export, or `ezpm.php` |
| Starter content (folders, a front page, demo items) | `contentobject` | content object export |
| Your extension, for others | `extension` | extension export, or Composer ([Packages (.ezpkg)](../extension-development/part-7-releasing/packages-ezpkg.md)) |

`ezpm.php` builds packages from a shell, so the same command runs for every release
([Creating packages with ezpm](../site-packages/your-own/creating-packages-with-ezpm.md)); the wizard is described in
[The package wizard](../site-packages/admin-gui/the-package-wizard.md).

## A site package of your own

A site package of your own pays off when you install the same kind of site many times (an agency's starter, a
franchise, training labs) or must rebuild an installation exactly. The path: fork an existing site package, change its
classes, content and installer script, rebuild the archives, version them, publish them on a package server, and point
installations at it ([Making your own site package](../site-packages/your-own/README.md)). The documentation
requirements a published package must meet are in [The requirements checklist](../site-packages/requirements/the-requirements-checklist.md),
and a package useful to others can be contributed to the shared server
([Contribute your site package](../site-packages/contribute-your-site-package.md)).

## Testing

Test a package where nothing can be lost: a separate checkout with its own SQLite database, a dry run, a full install,
a look at the result, then remove the sandbox ([Testing in a sandbox](../site-packages/your-own/testing-in-a-sandbox.md)).
Never run an installer against a database that holds anything you care about; the console install empties the
database it is given.

## What packages do not carry

- **Layouts.** Layouts and their rules travel with `exp:layouts export` and `import`, or in a theme extension's data
  files ([Layouts for CMS developers](layouts-for-cms-developers.md#layouts-between-installations),
  [Layouts data and share DBA](../site-packages/sevenx-multisite/layouts-data-and-share-dba.md)).
- **Machine settings.** `settings/override/` is written per machine.
- **Your code.** Extensions come from Composer or Git, not from content packages.
